# 边缘机配置件说明

本目录是边缘机上线前唯一需要按现场改写的配置来源。三个文件各自职责如下：

| 文件 | 作用 | 改写时机 |
| --- | --- | --- |
| `config.ini` | 运行参数（相机路数、采集与识别目录、模型路径、超时） | 换机型、换模型时 |
| `roi_binding.csv` | ROI 对照表：几何、货位、工具、标志类别的唯一台账 | 现场标定 ROI 与标志类别时 |
| `class_item_map.csv` | 类别组合到物品名的映射 | 更换物品类别体系时 |

## 一、roi_binding.csv

表头固定十二列，顺序不可调换：

```
roi_id,worker_id,drawer_id,position,tool_id,required_type,marker_id,confidence,rect_x1,rect_y1,rect_x2,rect_y2
```

| 列 | 含义 | 约束 |
| --- | --- | --- |
| `roi_id` | ROI 唯一标识 | 非空 |
| `worker_id` | 归属的采集线程编号 | 取值 1~4，第 N 号线程对应「左路第 N 台 + 右路第 N 台」两台相机；不得超过实际采集线程数 |
| `drawer_id` | 所属抽屉或柜组 | 非空 |
| `position` | 物理货位号 | 非空，全表不得重复 |
| `tool_id` | 该货位应放的工具编号 | 可为空，空串表示该货位不登记工具 |
| `required_type` | 该货位应放的工具类型名 | 供人工核对，不参与自动匹配 |
| `marker_id` | **模型训练出的标志类别名** | 非空；必须与推理结果里的 `className` 逐字相同 |
| `confidence` | 标志匹配置信度下限 | 缺省 0.85，取值 0~1 |
| `rect_x1/rect_y1/rect_x2/rect_y2` | ROI 四角点 | 左上角与右下角像素坐标，参照系是**拼接全景**；`rect_x2 > rect_x1` 且 `rect_y2 > rect_y1` |

### 1. marker_id 必须等于训练出的类别名

匹配逻辑：单标志直映时按 `className` 与 `marker_id` 等值比较；配置了类别组合表（`class_item_map.csv`）时按组合包含判定——检测出的类别集合包含该标志对应的组合键即命中、允许出现其它类别，命中置信度取参与匹配各项的最小值（组合识别取最低置信度，防止单个高置信类别带过整组合）。
因此 `marker_id` 填的不是工具编号、不是货位号，而是**该 ROI 内那个标志物在模型里的类别名**。
样例里的 `mk_8821`、`mk_8822` 是占位值，**上板时必须替换成现场训练出的标志类别名**，否则该货位永远判未识别。

### 2. 四角点的参照系是拼接全景

拼接全景由左右两路各取半幅横向拼成，尺寸等于单路相机原图的宽（原图宽的一半 × 2）与两图较小的高。
样例按骨架占位图 640×480 铺满四象限；**换真相机后必须按实际全景尺寸重标四角点**，
否则该行按未识别上报并在日志里留下越界原因，不会拖垮整轮扫描。

### 3. worker_id 与相机的对应关系

相机按 `config.ini` 的 `camera_indices` 顺序编号，左路在前、右路在后，
第 N 号采集线程拿「左路第 N 台 + 右路第 N 台」。例：`camera_indices = 1,2,3,4,5,6,7,8`
时，线程 1 是 cam1+cam5，线程 2 是 cam2+cam6，线程 3 是 cam3+cam7，线程 4 是 cam4+cam8。
`worker_id` 超过实际相机对数时启动即判配置错误，不会静默丢行。

## 二、class_item_map.csv

两列：`class_names`（逗号分隔的类别组合，顺序无关）、`item_name`（物品名）。
用于「一个货位里同时出现多个类别」的场景，例如 `person,surfboard` 折算成 `滑板人偶`。

匹配优先级：先按类别组合查本表折算成物品名，物品名与 `marker_id` 相同即算命中；
组合查不到时，再退回到单类别名与 `marker_id` 直接比较。两张表同时存在不冲突，组合表优先。
本表文件不存在时不装载，识别只走单标志匹配。

## 三、config.ini 关键项

| 节与键 | 含义 |
| --- | --- |
| `usb.camera_indices` | 相机索引列表，顺序即物理编号，左路在前 |
| `usb.capture_mode` | `auto` / `single` / `dual`，决定单摄还是双摄 |
| `usb.frame_source` | `camera` 真取帧，`placeholder` 用占位图兜底 |
| `usb.save_dirs` | 各采集线程的落盘目录；数量不足时按同类目录自动补齐，多出的舍弃 |
| `recognition.model_path` | 模型权重路径 |
| `recognition.roi_binding_csv` | ROI 对照表路径 |
| `recognition.require_roi_binding` | 装载不到对照表时是否启动即失败，见第四节 |
| `recognition.infer_timeout_sec` | 单次推理超时上限 |
| `recognition.aggregation_timeout_sec` | 一次全柜扫描的聚合等待上限，超时按降级出帧 |
| `recognition.inference_backend` | 推理后端，`ultralytics` / `onnxruntime` / `rknn`，默认 `ultralytics` |
| `recognition.nms_iou_threshold` | 同类别非极大值抑制的重叠阈值，默认 0.45 |

## 四、启动期校验口径

**对照表是识别的唯一事实来源**：识别只按本目录的 `roi_binding.csv` 装配，
不从 `config.ini` 读取 `roi_config`、`class_item_map`、`roi_bind_map` 之类的查表字典；
装配时传给识别门面的这三项固定为空字典。理由：当前三条推理后端产出的检测结果只有类别名与
置信度，没有区域编号，按区域归集必然塌缩，查表只能得到清一色的未识别条目，
看着像正常结果其实是故障。

装载不到对照表（文件缺失、只有表头没有数据行、装载失败）时，按 `[recognition]`
的 `require_roi_binding` 分两种口径，详见 `../README.md` 第 3.6 节：

| `require_roi_binding` | 装载不到对照表时的行为 |
| --- | --- |
| `false`（现场默认值） | 不阻断启动：记一条 error 级日志，识别能力置为不可用，周期帧照发；收到识别请求立即回一帧 `items` 为空的合法应答 |
| `true`（生产严格口径） | 启动即失败，抛 `[CONFIG]` 配置错误，防止识别带着空台账上线 |

其它装配期就直接判配置错误的问题：对照表缺列、必填列为空、矩形非法、货位重复、
线程编号越界、类别组合表必填列为空。运行期若某路相机打不开或连续取图为空，
该路货位按未识别补进清单，上位机仍能收到形状完整的应答，不会因为一路故障收不到回应。

## 五、推理后端口径

| 后端 | 权重格式 | 说明 |
| --- | --- | --- |
| `ultralytics` | `.pt` | 项目原实现路线，默认后端 |
| `onnxruntime` | `.onnx` | 纯 onnx 权重直跑，输出上补做同类别非极大值抑制 |
| `rknn` | `.rknn` | RK3588 板端 rknnlite NPU 推理；输出与 onnx 同源并补做 NMS；当前只支持单输出检测矩阵，需上板标定 |

**换后端等于换结论**：三条后端的预处理口径（缩放方式）与类别映射尚未逐项对齐。
实测同一张样例图，ultralytics 出 6 条，onnxruntime 抑制前出 62 条、
按 0.45 阈值抑制后出 8 条，差异来自缩放口径与低分误检，不是抑制阈值的问题。
因此 `onnxruntime` 分支**未与 ultralytics 对齐，需现场标定**，
默认后端固定为 `ultralytics`；现场要用 onnx 权重时，改配置后必须重新标定标志类别名与置信度门槛。

## 六、摄像头状态口径

周期帧 `camera_status` 里每路相机只有一个状态，取值只有两种：

| 状态 | 含义 |
| --- | --- |
| `ok` | 这路相机探测可达、成功打开过且能正常取图 |
| `offline` | 这路相机不可用：设备缺失、从未成功打开过或取图失败 |

照度不足、镜头脏污需要图像分析判定，当前版本不设这两种取值、也不上报。
取图失败归到 `offline`，不单独设通信异常状态。
上位机拿 `camera_status` 做开柜闸门，任何不可用的相机一律报 `offline`，
不会被误判成可用后放行开柜、却因为没有图像导致识别必然失败。

## 七、相机编号与索引口径

`usb.camera_indices` 的**顺序**决定物理编号：第 N 个索引对应周期帧里的 `CAM{N}`。
左路相机排在前、右路相机排在后，第 N 号采集线程拿"左路第 N 台 + 右路第 N 台"两台。
索引的**取值**直接作为图像处理库的设备索引使用，Windows 下按 0 起编号；
现场若按 1 起编号安装，必须把配置改成实际取值，否则末路相机会一直报 `offline`。
