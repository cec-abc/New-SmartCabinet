## 1. 这个系统是做什么的

一句话业务闭环：**上位机（带界面的柜机程序）先开柜，用户取放工具后关柜，上位机向边缘机发一帧 `recognize_req`；边缘机驱动 8 路摄像头抓图、拼接、推理，把"每个货位 detected 了什么"整理成 `recognize_ack` 清单回给上位机；上位机拿这份清单跟自己库里的在库记录比对，判出借用/归还/错放，再写库**。

边缘机（`edge/`）在这条链里只负责两件事，不碰业务、不碰数据库：

- **如实上报柜内实况**：8 路相机的实时状态放进周期帧 `periodic`，每 3 秒一帧发给上位机；上位机拿 `camera_status` 做开柜闸门——任一路报非 `ok` 就拒绝开柜。
- **收到请求就回清单**：收到 `recognize_req` 就回一帧 `recognize_ack`，`items[]` 覆盖全部登记货位；识别不出来也必须回一帧结构合法的清单（未识别条目），不能沉默让上位机干等超时。

边缘机是**后台服务进程，没有图形界面**。看不到窗口是设计如此，不是故障。它是 TCP **客户端**，主动去连上位机（上位机是服务端，监听 `config.ini` 里的 `tcp.port`，默认 9000）。"开柜"动作由上位机下发 `open_req`，但 IO 板硬件尚未接入，边缘机目前一律回失败并写明原因——这是如实上报，不是缺陷。

三条贯穿全工程的既有裁决，读代码时处处会碰到，先记住：

- **D-01**：自检只留空接口（`selfCheck` / `selfCheckSystem` / `selfCheckRecognition`），本轮不实现、不新增自检线程。
- **D-02**：非链路 UP 不启动业务线程；系统启动时只拉 TCP 重连线程，连上后才启心跳与解码线程。
- **D-03**：请求去重只按 `request_id`，`seq` 字段只填不用。
- **D-20（2026-11-16）**：断链补报能力已删除，`EventCache` 整套机制已移除；断链期间不缓存事件、恢复后不补发。旧文档/旧图里若有"EventCache 补发"字样，是历史快照，不是当前实现。

## 3. 一次识别请求的完整调用链

从收帧到回 ack，按实际函数名顺序列出。这条链横跨 TCP → 控制 → USB → 识别 → 控制 → TCP，是排查"请求进来了但没回清单"的主线。

**收帧与分发（TCP → 控制）：**

1. `TcpSocket.recv`（`modules/tcp/tcp_socket.py`）阻塞收字节。
2. `TcpDecodeThread.runLoop` → `readNextChunk` → `dispatchFrames` → `TcpComm.splitFrames`（按 `\n` 切帧，处理半包/粘包，空行忽略）→ `dispatchOneFrame` → `TcpComm.decodeAndParse`（JSON 解析、超长/非对象判 FRAME_PARSE，坏帧丢弃不中断）。
3. 记一条 `RX` 日志（`TcpComm.buildIoLogPayload`），再 `sink.onSignalDecoded(decoded)`。
4. `TcpControlLayer.onSignalDecoded` 转发给上游 → `EdgeControl.onSignalDecoded` → `EdgeControl.routeSignal`。
5. `routeSignal`：`extractRequestId` 取协议 `request_id`；`reuseCompletedAck` 命中已完成请求则复用上次应答；`markRequestPending` 防同一请求重复扫描；再按 `signal["type"]` 从 `asyncHandlers` 字典取处理器（只有 `recognize_req` 一个键），调用 `handleRecognizeReq`。**控制层不认识任何业务字符串，只认注入的键。**

**触发采集（控制 → USB）：**

6. `handleRecognizeReq`（`app_init.py`）：识别能力不可用则 `emitEmptyAck` 立即回空清单；否则 `trigger.triggerCapture(requestId)`。
7. `CaptureTrigger.triggerCapture` → `invokeStartCapture` → `UsbController.beginScan(requestId)`。
8. `beginScan`：未在采集则 `_buildWorkers` 建 4 个 `CaptureWorker` 并 `worker.start()`（**并发拉起后立即返回，不等子线程**）；已在采集则给在跑的 worker `setRequestId` 换请求标识。

**取帧与帧回调（USB → 控制）：**

9. `CaptureWorker.runLoop` → `openCameras`（逐路 `camera.open`，完成即 `reportDevicesReady`）→ `waitFocusApplied`（等定焦屏障）→ 等 `focus_stable_ms` → `_captureStream`。
10. `_captureStream` 每轮 `captureOnce`（对组内每路 `camera.readFrame`）→ `_publishFrames`：先 `frameSink.onFrameCaptured(workerId, frames, requestId)` 回调（帧在前），再按需落盘和滚动删旧，成功回调每轮只报一次。
11. `EdgeControl.onFrameCaptured`：记下 `workerRequests[workerId]`；若该请求已应答则跳过；否则 `triggerRecognitionByFrames(workerId, requestId, frames)`。

**识别（控制 → 识别）：**

12. `RecognitionController.trigger` → `buildRecognitionWorker` → `RecognitionWorker.start`（每次触发新建实例；同 worker 上一轮没跑完则丢帧并计数）。
13. `RecognitionWorker.runLoop` → （对照表链路）`runTableRecognition` → `stitcher.stitch(frames)` 拼全景 → `runInference`（`timeoutRunner(engine.infer, inferTimeoutSec)`）→ 逐行 `recognizeRow`（`detectionsInRoi` 筛落在 ROI 内的检测 → `matchMarker` 匹配标志类别）→ `buildRowItem` 组条目 → `buildAck` → `emitResult` → `sink.onRecognitionResult`。

**聚合与出网（识别 → 控制 → TCP）：**

14. `EdgeControl.onRecognitionResult` → `collectAggregatedFrames`（按 `request_id` 把各 worker 的 items 存入 `_aggregations`）→ `completeRequestIfReady`（已上报线程数 + 已失败线程数覆盖期望的 4 个 worker 才出帧；`mergeWorkerItems` 按货位排序、去重货位保留第一条；失败线程的货位用降级条目补齐）→ `buildAggregatedFrame`（顶层只留 `type`/`request_id`/`items`，剥掉 `workerId`/`requestId` 内部字段）→ `enqueueFrame`（只入 outbox，不在回调里做 IO）。
15. `EdgeDispatchThread` 周期（默认 0.2s）`drainOutbox` → `EdgeControl.dispatchOutbox` → 链路上报探针 `syncLinkState`、超期请求 `collectExpiredFrames` 降级出帧 → `frameSender(frame)` → `TcpComm.encodeFrame`（出网守卫：未知帧型/超安全阈值先裁剪清单，记 `TX` 日志）→ `TcpSocket.send` 出网。

> 收不齐 4 路时的兜底：`_scanDeadlines` 记了聚合截止时刻（`aggregation_timeout_sec`，默认 5s），`dispatchOutbox` 里 `collectExpiredFrames` 会把超期请求未上报的 worker 全部按失败补齐，降级出一帧**形状完整**的清单。所以某路相机坏掉不会导致上位机收不到应答。

## 4. 8 路摄像头与 worker 的映射关系（最容易搞错）

这是新人最易出错的点，单独讲透。核心事实三句：

1. **`camera_indices` 的顺序决定物理编号**：第 N 个索引 = 周期帧里的 `CAM{N}`。配置 `camera_indices = 1,2,3,4,5,6,7,8` 时，设备列表按下标展开就是 CAM1~CAM8。索引的**取值**直接当图像处理库设备号用：Windows 按 0 起编号，现场若按 1 起安装就要填实际取值，填错末路会一直 `offline`。
2. **4 个 worker，每个拿前后各一路**：`app_init.buildCameraPairs` 把设备列表对半切，`pairs = [(devices[i], devices[i+half])]`。8 路时 `half=4`：

   | workerId | 左路（前半段） | 右路（后半段） | ROI 对照表归属 |
   | --- | --- | --- | --- |
   | 1 | CAM1（devices[0]） | CAM5（devices[4]） | worker_id=1 |
   | 2 | CAM2（devices[1]） | CAM6（devices[5]） | worker_id=2 |
   | 3 | CAM3（devices[2]） | CAM7（devices[6]） | worker_id=3 |
   | 4 | CAM4（devices[3]） | CAM8（devices[7]） | worker_id=4 |

   一句话记法：**第 W 号 worker = CAM{W} + CAM{W+4}（W=1~4），前半是左、后半是右，同序号配一对**。worker 内 `cameras[0]` 是左路、`cameras[1]` 是右路，拼接时左半幅 + 右半幅。

3. **逐路定焦按物理路号取值，不是 worker 内下标**：`focus_positions` / `zoom_positions` 各 8 个值，第 N 个值对应 CAM N（`下标 = 物理路号 - 1`）。`UsbController.applyFixedFocus` 遍历 `_cameraDevices`（按"先各组第 1 路、再各组第 2 路"的整柜顺序展开），用 `position` 直接索引配置数组。CAM5~8 虽然在 worker 内是第二路（下标 1），但必须取第 5~8 个配置值；若误按 worker 内下标 0/1 取，CAM5~8 会拿到 CAM1~4 的值，整柜定焦全乱。

补充口径，排障时要用：

- 定焦指令**在相机打开成功之后**才下发：`UsbController.onWorkerDevicesReady` 收集到全部 worker 就绪后，统一 `applyFixedFocus`，只记一条汇总日志（`N 路相机对焦已下发，模式 fixed` 或 `N 路相机对焦未生效：原因`）。开机时相机还没打开，不下发定焦，也不占用识别时间窗。
- `focus_stable_ms`（默认 200）在定焦下发后等镜头稳定，经 `interruptibleWait` 可被停机打断。worker 内还有 `waitFocusApplied` 屏障，保证先就绪的线程不会在别人还没定焦时抓到糊帧。
- **单摄/`layer_mode=single` 例外**：`capture_mode=single` 时每个索引自成一个 worker（N 路 N 个 worker），不拼接；`layer_mode=single` 是工装单层测试，只取前 2 路构成 1 个双摄 worker，其余链路不变。此时对照表行号会由 `normalizeRoiWorkerIds` 归并到实际 worker 数内，货位总数不变。
- 相机状态只产出两种值：`ok`（可用）/ `offline`（不可用：设备缺失、从未成功打开或取图失败）；照度不足、镜头脏污需要图像分析，当前版本不设这两种取值，取图失败也不单独设状态、归到 `offline`。
- 这组映射有专门的固化用例 `edge/tests/integration/test_camera_mapping_chain.py`，改映射逻辑前先看它断言了什么。

## 5. 配置项速查

改配置只改 `d:\CFDZ\BYJSJ\New-SmartCabinet\edge\config\config.ini`。相对路径按"运行时工作目录 → `edge/` → 仓库根"逐级查找；默认从仓库根启动（`run_edge.bat` 会 `cd` 到仓库根），所以 `./logs` 落在仓库根的 `logs/`。

| 配置项（节.键） | 作用 | 当前值 | 修改影响 |
| --- | --- | --- | --- |
| `tcp.host` | 上位机地址（边缘机是客户端去连） | `127.0.0.1` | 改成现场上位机实际 IP；填错连不上、周期帧发不出 |
| `tcp.port` | 上位机监听端口 | `9000` | 与上位机监听端口不一致则连不上，观察工具默认也监听这个端口 |
| `tcp.connect_timeout_sec` | 连上位机超时秒数 | `5.0` | 超时按 `backoff_seq` 退避重连 |
| `tcp.recv_timeout_sec` | 单次收包超时 | `0.5` | 超时是正常轮询节拍，不算断链；改大停机收敛变慢 |
| `tcp.max_frame_size` | 单帧字节上限 | `1048576` | 超长帧按 FRAME_PARSE 丢弃；出网安全阈值取其一半（且不超过上位机硬上限 1MB 的一半） |

| `tcp.heart_interval_sec` | 周期帧发送间隔 | `3` | 上位机靠这个判"边缘机还活着"，改大可能触发上位机离线判定 |

| `usb.frame_source` | `camera` 真取帧 / `placeholder` 占位图 | `camera` | 无相机或没装图像处理库时用 `placeholder` 兜底 |
| `usb.save_frames` | 采集帧是否逐路落盘 | `false` | 生产口径 `false`（只走内存回调）；调试设 `true` 存单图。缺键按开启处理 |

| `usb.focus_positions` | 8 路逐路焦点，按 CAM1~8 顺序 | 8 个 `0.0` | 第 N 个值对应 CAM N；填 1 个值广播给 8 路；上限 125，须逐路用 lab 工具实测 |
| `usb.zoom_positions` | 8 路逐路变焦，顺序同上 | 8 个 `0.0` | 规则同上；上限 1020；多数定焦 USB 摄像头硬件不支持 |
| `usb.focus_stable_ms` | 定焦下发后等镜头稳定的毫秒数 | `200` | 改大首帧更稳但更慢；转成秒交给可打断等待 |
| `recognition.model_path` | 模型权重路径 | `./weights/yolov8n.pt` | 换模型改这里；模型只在 `init` 时 `loadModel` 一次 |
| `recognition.infer_timeout_sec` | 单次推理超时上限 | `3.0` | 超时按 INFERENCE_TIMEOUT 逐行降级为未识别 |
| `recognition.aggregation_timeout_sec` | 全柜扫描聚合等待上限 | `5.0` | 超时未收齐 4 路就降级出帧，防止上位机收不到应答 |
| `recognition.roi_binding_csv` | ROI 对照表路径 | `./config/roi_binding.csv` | 识别的唯一事实来源；缺表按 `require_roi_binding` 处理 |
| `recognition.require_roi_binding` | 装载不到对照表是否启动即失败 | `false` | `false`：不阻断、周期帧照发、请求回空清单；`true`：启动即失败（生产严格口径） |
| `recognition.inference_backend` | `ultralytics` / `onnxruntime` | `ultralytics` | 两后端未对齐，换后端等于换结论，须重新标定；默认固定 ultralytics |
| `recognition.nms_iou_threshold` | 同类别非极大值抑制 IoU 阈值 | `0.45` | 仅 onnxruntime 分支补做 NMS 时用 |
| `recognition.save_panorama` | 是否存拼接全景大图 | `false` | 生产 `false`；调试标 ROI 设 `true` 写全景到识别目录 |

配置里的相机路数、采集/识别目录数、ROI 对照表 `worker_id` 三者必须自洽：`worker_id` 超过实际 worker 数，装配期直接抛 CONFIG；某组在对照表里没有货位，启动时会记一条 error 说明"这几路相机是白开的"。

## 9. 常见问题排查

**Q：启动报 `ModuleNotFoundError: No module named 'edge'`。**
不在仓库根跑。到 `d:\CFDZ\BYJSJ\New-SmartCabinet` 执行 `python -m edge.main`，或双击 `edge\run_edge.bat`。`python edge\main.py` 这种写法不行（脚本目录会成为模块搜索路径首位）。

**Q：报 `AttributeError: module 'platform' has no attribute 'python_implementation'`。**
在 `edge/` 目录里直接跑，`edge/platform/` 包遮蔽了标准库 `platform`。回仓库根跑即可。程序启动时也会主动把 `edge/` 从模块搜索路径摘掉（`detachEdgeModuleDirFromSearchPath`），但根因仍是启动位置不对。

**Q：报 `[CONFIG] 已有实例运行，进程锁获取失败` / 测试里 fcntl、锁相关报错。**
进程锁文件是 `edge_runtime.lock`，放在**启动时的工作目录**。已有实例在跑：先结束旧进程或在旧窗口按 Ctrl+C，再启动；**不要直接删锁文件**（进程还在跑时删了也拦不住重复启动）。关于 fcntl：Windows 侧进程锁走 `msvcrt.locking`（`platform/adapter.py` 的 `WindowsAdapter.lockFile`），Linux/麒麟侧走 `fcntl.flock`（`LinuxAdapter.lockFile`，fcntl 在函数体内导入避免 Windows 引入无关依赖）。单测不碰真实系统锁——`FakePlatformAdapter` 用构造注入的 `lockResult` 模拟"锁被占用/取锁成功"，所以单元测试里不应出现真实 fcntl/msvcrt 调用；若单测报 fcntl 相关错误，多半是误把真实 `ProcessFileLock` 用在了 Windows 环境或没注入 Fake。真实双进程取锁属上板项，当前未在真机验证。

**Q：日志报 `[CONFIG] 配置文件缺失: ...`。**
确认 `edge\config\config.ini` 在位。默认配置路径固定指向 `edge/config/config.ini`，与启动工作目录无关；若改成相对路径，则按"运行时工作目录 → `edge/` → 仓库根"逐级查找，三处都没有才报这个错；改成绝对路径则直接查该路径、不回退。

**Q：上位机看不到周期帧 / 连不上。**
按顺序查：① 上位机有没有在 `tcp.host:tcp.port` 上监听（边缘机是客户端，上位机不监听就连不上）；② 日志有没有 `link UP`，没有就看 `连接失败` 和退避重试记录；③ 防火墙是否放行端口；④ 用 `watch_periodic` 桩上位机起在同端口，看边缘机能否接入并按 3 秒一帧发。注意不要同时开两个"上位机"（真上位机和桩观察工具）抢同一端口。

**Q：周期帧里相机全是 `offline`。**
相机没接，或 `camera_indices` 的取值与实际设备号对不上。`camera_indices` 的顺序决定 CAM1~8 编号，取值直接当设备索引：现场按 1 起编号就填 `1..8`，按 0 起就填 `0..7`，填错末路一直 offline。没接相机属正常现象：周期帧照发、8 路如实报 offline、上位机按 offline 拒绝开柜，不会误开柜。

**Q：对焦找不到清晰点 / 画面糊。**
用 `manual_focus_test.py --device N` 逐路手动调：先看窗口打印的硬件能力探测（对焦是否支持），再用左右/上下键粗调微调找到清晰点，按 `r` 回读当前 `focus`/`zoom` 值，把这个值填进 `focus_positions` 对应路号位（第 N 个值 = CAM N）。若不确定硬件上限，先跑 `getFocusZoomRange.py`（记得改脚本里写死的设备号）测出真实上限。定焦是相机打开后才下发的，改完配置要重新触发一次识别扫描才生效；`focus_stable_ms` 太小可能抓到未稳定的首帧，可适当调大。

**Q：识别请求发出去了，上位机说没收到应答 / 清单为空。**
看日志关键字：`module: TcpTx` 且 `request_id` 等于该请求——没有这条就是没出网，再看 `ERROR` 里的出网拦截原因（未知帧型、清单超阈值被裁剪）；有这条则看 `frameBytes`，超 4096 会被折叠、`itemsCount` 是原始条数，逐条清单去上位机收帧处核对。清单为空先查 `识别能力不可用：未装载 ROI 对照表`——现场口径 `require_roi_binding=false` 时缺表会降级回空清单，这是设计行为；补齐 `roi_binding.csv` 或按生产口径设 `true` 让它启动即失败。

**Q：切到笔记本摄像头后 `output/capture/w1/` 一直是空的。**
采集是**按需触发**的：启动后只发周期帧，只有收到 `recognize_req` 才拉起采集线程抓帧。用 `watch_periodic 9000 0 req` 接入后主动发一帧识别请求触发采集，再去看落盘的 JPEG。单摄（`camera_indices=0`）会把 4 个 worker 缩成 1 个，落盘在 `w1/`。

**Q：测试里那条 `PytestConfigWarning: Unknown config option: pythonpath` 要不要管。**
本机 pytest 6.2.4 低于 `pyproject.toml` 声明的 `pytest>=7.4,<9`，`pythonpath` 选项不识别而已；仓库根已在 `sys.path`，用例收集和通过数不受影响。彻底消除需升级 pytest 或改 L1 声明，两者都要用户批准，当前仅如实登记。
